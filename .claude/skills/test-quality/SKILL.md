# Foundational Principle

**Tests must be deterministic.** A test that passes or fails depending on timing, ordering, or environmental state is worse than no test — it erodes trust in the suite. Every assertion must compare against a known, fully predictable value. If a value cannot be predicted (e.g., UUIDs, timestamps), control it via fixture or an injected value (a clock, a start time), never ignore it. If you find yourself writing a containment check (`in`, `<=`) because you're unsure of the full result, that's a signal to pin the expected value, not weaken the assertion.

**Get-or-create in test setup is a code smell.** Each test starts from its own `tmp_path` and a new git repo — there is no pre-existing file or object to "get." A get-or-create step in test setup (`mkdir(exist_ok=True)`, `if not path.exists(): path.write_text(...)`, `dict.setdefault`) always takes the "create" path, so the get-or-create semantics add nothing; they only obscure intent. Worse, they suggest the test is hedging against non-deterministic prior state, which violates the foundational principle. Use a Factory Boy factory or a direct write instead — these make the intent unambiguous ("I need this to exist") and fail loudly if it unexpectedly already exists. Reserve get-or-create for the production code it belongs to; test the idempotency semantics of that production code explicitly when they matter, don't lean on them silently during setup.

**The narrow exception — an exact fragment inside a larger value another component owns.** Containment is legitimate, *not* a smell, when all three hold: (a) the asserted fragment is **exact and complete** — a whole line, token, or value the SUT itself produces, spelled out in full, not a loose substring hedging against an unknown; (b) it is embedded in a **larger composite owned by a different component** (a value assembled, formatted, or templated elsewhere), so the surrounding text is not the SUT's product; and (c) asserting the whole value with `==` would pin that other component's content, making the test a brittle tautology that breaks on unrelated edits to code the test does not target. The discriminator: are you loosening to `in` because you can't predict the SUT's output (smell — pin it), or because the SUT's exact output is one part of a larger value you deliberately don't want to assert whole (legitimate — the `==` would test the wrong component)? When the exception applies, still assert the *complete* fragment, never a partial one.

**"Owned by a different component" turns on content authorship, not on who runs the `join`.** A SUT that *assembles* a string — collects sections into a list and `"\n\n".join`s them — does not thereby *own* the content of each section when that content is authored elsewhere: a loader reading a verbatim `.md` file, a separate formatter producing a sub-section, a templated block. The bulk of the composite belongs to those collaborators; the SUT owns only the *selection and ordering*. So asserting one section with `==` (extracted via a `_section_lines(text, title)`-style helper that returns the exact, complete section) is the gate-3 exception, not a violation — a whole-string `==` would pin the fragment files' content and break on edits to code this test does not target. Worked example: `JudgeRequest.prompt` wraps the rule's skill text, read verbatim from its `SKILL.md` by `Skill.from_file`, and the changes `JudgeRequest.of_change` rendered; breaking the prompt's wrapping fails the asserted `<rule name=...>` line, but editing an unrelated rule's `SKILL.md` does not — exactly the robustness of a good test. The smell-test that separates this from a real violation: does breaking the *logic under test* fail the assertion while an unrelated-collaborator edit leaves it green? Yes ⇒ exception applies.

# Testing Quality Gates

Before writing any test, verify it adds signal:

1. **No-signal tests** — Every test must answer: *what change to my own code would make this fail?* If the only way to break it is editing the declaration it mirrors (tautology), breaking the framework (Pydantic/stdlib defaults, type-acceptance, serialization), or breaking already-tested generic code (true redundancy), it adds no signal — don't write it. Deciding question: *if it went red, would I fix the code or the test?* See [references/signal-and-mocking-gates.md](references/signal-and-mocking-gates.md) and [references/redundant-tests.md](references/redundant-tests.md).
2. **Real objects over mocks** — `MagicMock`/`patch()` are acceptable **only at the process boundary** (HTTP to third-party APIs, cloud SDK calls leaving the machine, services needing external credentials; codeguard's judge CLIs — claude, codex, gemini — are replaced by fake CLIs at that boundary). Git and the filesystem are NOT a boundary — use a real temporary git repo and `tmp_path`; never mock git output, file reads, or any collaborating class. **Never `patch()` internal functions, factories, or module-level callables** — inject the dependency or use a real-object test helper instead. Search for an existing shared stub before writing an inline one. **`monkeypatch.setattr` is `patch()` by another name — the same rule applies.** Reassigning a module-level constant, function, or attribute of the SUT *so that real work doesn't run* (e.g. `monkeypatch.setattr(sut_module, "build_import_graph", lambda: {...})`, or repointing a `REPO_ROOT` constant to dodge a real filesystem walk) is stubbing the thing under test — inject the dependency instead (pass a value object / param the test constructs) and let the real code execute against it. Do **not** justify it by analogy to `monkeypatch.setenv`/`mock.patch.dict(os.environ)`: those are the *narrow* exception, sanctioned only for **exercising** settings-, feature-flag-, or environment-dependent behavior (the value being varied *is* what the test is about), never as a backdoor to replace a collaborator or stop production logic from running. If you find yourself drafting a paragraph explaining why your internal patch is a "justified exception," that is the signal to build the dependency-injected version first — it is almost always achievable and usually surfaces a seam the production code was missing. **Never substitute empty/dummy data to bypass a failure** — that failure is a production bug to fix, not to hollow out (`make_binding(triggers=frozenset())` where real triggers belong hides the path that matters; it's acceptable only in wiring tests the SUT provably doesn't exercise). **Seed through production's creator; never fabricate a reference to dodge creating its parent** — when one production creator (a builder, a `from_config`/`of_change` constructor, a service method) makes an object, seed through it or a thin helper that drives it; a hand-rolled construction loop in `conftest` paralleling the creator is gate-10 shadowing, and a child given `source_id=str(uuid4())`/`*_id=<fresh uuid>`, or a path to a file never written, pointing at a never-created parent is the tell (a missing check that the reference resolves is a modeling gap to fix, not to exploit). **Do not fabricate runtime identity just to satisfy an over-wide setup object.** A fixed UUID/session id/job id constant in a test fixture is a hard stop unless the SUT actually correlates on that identity and the corresponding real object exists or is asserted. If the id is only needed because a broad context/factory constructor requires it while the fixture returns a narrower static value, narrow the setup to the real inputs instead of building the runtime context. **A shared fake abstracts one layer — extend it by configuration, never by cross-layer subclassing.** Don't subclass a shared fake (`RecordingJudge`, `ScriptedGemini`) to override a method so the override asserts internally or queries a *different* subsystem (e.g. overriding a judge fake's `judge` to read the judgement cache's store). Use the fake directly and assert on its observable in-layer state in the test body; a genuinely lower-layer invariant earns its own test at that layer. Preference order: real object → shared stub/fake → inline protocol stub (framework contract tests only) → `patch()`/`MagicMock` (boundary only). **Drive through the production factory, never rebuild its graph or derivation in test code.** When a production factory (or builder/creator) already assembles an object graph, the test must call that factory — injecting a test double for the boundary collaborator (e.g. a `RecordingJudge`) via the factory's constructor or a parameter added for DI. A fixture that manually reconstructs the same graph the factory builds (instantiating the same internal collaborators, wiring the same plumbing) is a parallel reimplementation that drifts from production: when the factory changes, the test keeps passing against a stale graph, providing false confidence. The correct response to "the production factory doesn't accept my test double" is to add the DI seam to the production factory (a constructor param with a production-default), not to bypass the factory in test code. This is exactly what dependency injection is for — testability is decoupling. The fixture becomes a one-liner: `ProductionFactory(runner=recording_runner).create(...)`. **The same rule covers derivation, not just wiring.** When a production factory derives intermediate values from its input (inspects a spec to compute `element_type`, walks annotations to find an identity field, resolves a strategy from a mode enum) and the test fixture reimplements that same derivation to construct the output type directly — that is the derivation-drift variant of the same defect. The factory's derivation logic changes and the fixture keeps passing against a stale derivation. Fix: build the factory's *input* (e.g. a `Binding` with the right attributes via `make_binding`, and the file in a `GitRepo`) and call the production factory (`JudgeRequest.of_change`), then take the result (or a public attribute of the result like `.changes`). See [references/signal-and-mocking-gates.md](references/signal-and-mocking-gates.md). For how to construct and parameterize the factories and fixtures themselves — the correct shape once you have the DI seam — follow the `pytest-factoryboy` skill.
3. **Prefer `==` over `in`** — Exact equality when values are deterministic; a containment check signals you should pin the value, not loosen the assertion. *Exception:* containment is legitimate when the asserted fragment is exact and complete, embedded in a larger composite a **different component** owns, and a whole-value `==` would pin that other component's content rather than the SUT's — see the Foundational Principle. The fragment must still be complete, never partial.
4. **Assert on result objects, not fields** — Instantiate the expected object and assert equality (`assert result == MyModel(name="Alice", age=30)`), so an unexpected side effect on a *sibling* field can't pass unnoticed. A bare `len()` check is the same weakness; consolidate per-index checks into one structural assertion (`assert [s.key() for s in items] == ["a", "b"]`). **Whole-object `==` is required whenever the result type has `__eq__` — asserting every field individually with separate `==` lines is still a violation, even when it covers all of today's fields.** The field-by-field form passes today but silently fails to guard any field *added later*; the whole-object `==` is precisely what buys that future signal, so a "but I checked all the fields" test is not equivalent and must be consolidated. Field-by-field is correct ONLY when equality is genuinely impossible (no `__eq__`, generated ids, timestamps) or the return is a scalar — and then assert ALL observable fields, never a tuple comparison, which strips field names. See [references/signal-and-mocking-gates.md](references/signal-and-mocking-gates.md).
5. **Reuse and construction hygiene** — Reusing a shared `make_<type>` builder or fake before writing a local one, the factory-vs-helper decision, and seeding parent-owned children through the parent creator are all governed by the `pytest-factoryboy` skill; load it before writing any fixture, factory, or construction helper.
6. **Eval inputs must differ from instruction examples** — Eval cases that reuse text from the judge's instructions (`src/codeguard/review/judge.md`) or the rule's `SKILL.md` test memorization, not generalization. Use different domains, phrasing, and values.
7. **Evals follow the eval guidelines** — Each dataset covers one task with a plain task function that calls the LLM the way production does and returns the projected value its cases compare; expected results live in `Case.expected_output`, compared with built-in evaluators; one case per input, comparing that input's whole projected output; no shared runner, no task retries, and one report assertion that fails on any failed case, evaluator error, or raised task. The rules and examples are in [eval-testing-guidelines.md](../../../docs/claude/eval-testing-guidelines.md), imported below. These rules cover codeguard's own LLM tests and evals (`pytest -m llm`); they do not cover `JudgeEvalRunner` and `codeguard eval`, which are product features codeguard ships for rule packages to evaluate their judge rules.
8. **Test names must match assertions and implementation vocabulary** — The name must describe what the assertion proves, not how it's implemented. Use the same terminology as production code — no synonym drift (inject vs resolve, build vs assemble). **Never coin a phrase for a state that already has a term** — name the condition with the production symbol or standard engineering word, not an invented or metaphorical stand-in (`test_quiet_judge_*` for a verdict with no violations is invented; the real condition is *no violations* → `test_no_violations_*`). Tell: a noun/verb in the name that appears nowhere in the code under test and has a plainer equivalent that does.
9. **Fixture design** — Fixture shape (one object per fixture, never a tuple; setup-only fixtures kept apart from data fixtures) is governed by the `pytest-factoryboy` skill; load it before writing fixtures.
10. **A test helper may set up, never perform the act under test** — A helper reduces setup boilerplate (assemble the object graph, write files to a `GitRepo`, build inputs and the SUT); it must not absorb the *act* the test verifies. Two ways it crosses the line: (a) **computing** a value production already computes (an id, key, hash, ordering) by importing the same builder/allocator — a helper named after one domain/scenario is the tell; (b) **ending by calling a method/attribute on the object it built and returning that result instead of the object** — `return Mapper(specs).map(x)`, `return build_y(...).resolve(z)`, `return make_judge_request(...).prompt`. This holds *regardless* of whether the method is the one under test: a construction helper must return the constructed type. (Calling methods *while building* — builder chains, factories, constructors — is fine; the test is what it **returns**: the assembled object, or a terminal call's output layered on top.) Fix (a) by sourcing the value from the production path or mocking at a higher seam; fix (b) with **two helpers** — one returns the built type, a separate action-named helper (or an inline test-body line) makes the call. **Exception to (a):** calling the production function in the *expected value* is fine when the value is a deterministic **output** field the SUT *delegates* to a collaborator, its inputs are asserted in the same expected object, and the collaborator's function is pinned independently by its own test (a *consistency* check, not a clone of SUT logic). See [references/helper-and-integration-gates.md](references/helper-and-integration-gates.md).
11. **Sourcing values for a test** — Tracing a needed value (id, ref, key) back to the factory input that first produced it — rather than digging it out of an assembled result or a child object — is governed by the `pytest-factoryboy` skill.
12. **Do not normalize the result before asserting** — Assert against the result the SUT actually returns; don't rebuild it with `replace`, `model_copy(update=...)`, `model_dump(exclude=...)`, or a stripping comprehension before the `==`. Every field edited out is a field no longer guarded (gate 4 silently downgraded to partial). Instead, navigate to the single noisy field and assert its meaningful part directly (`assert issue.context["input"] == "high"`) while asserting the surrounding object normally. Needing normalization also signals the seam is too wide. See [references/helper-and-integration-gates.md](references/helper-and-integration-gates.md).
13. **Construction-helper parameters** — Helper/factory signatures (declare typed params; a `**kwargs`/`**overrides` bag only as untouched pass-through to one typed sink; no alternative-input branching; no production-sounding aliases for test-only shapes) are governed by the `pytest-factoryboy` skill.
14. **Helpers earn their existence** — Dead parameters and thin-wrapper shims (single call site, one-constructor pass-throughs, closure fixtures, re-passed defaults, and the load-bearing-annotation carve-out) are governed by the `pytest-factoryboy` skill.
15. **Test data through fixtures** — Constructing test data in fixtures rather than module-level constants, and a test owning any identity value it asserts on, are governed by the `pytest-factoryboy` skill.
16. **Test object construction follows the pytest-factoryboy skill** — Every fixture/factory/construction decision — module-level helpers, module constants, inline vs `@pytest.fixture` vs FactoryBoy `Make*`, and the ban on fixture-returning-callables — is governed by the `pytest-factoryboy` skill; load it before constructing any test object or harness. There is **no** fixture-factory-closure exemption: a fixture returning a callable is an antipattern there, always convertible. The only legitimate module-level functions in test files are trivial callbacks the SUT or a framework hook takes as an argument (e.g. `def _no_answer(messages, info): raise AssertionError` passed to `FunctionModel`) — these are callbacks, not construction helpers.
17. **Arrange, Act, and Assert stay in the test body — never abstracted away** — The three phases of a test — *arrange* (build the preconditions), *act* (invoke the SUT), *assert* (check the outcome) — are the test's own responsibility and must be visible in the test method. **Construct the SUT in the test body** — fixtures and helpers build only its collaborators and inputs, so the act's target is visible beside the act (`thing = Thing(dep)` then `thing.run(x)`; a `make_*` factory call in the body counts). A fixture supplies a **thing** (an object or datum via the DI graph); it must not perform *arrange actions* — starting the SUT's workflow/job, advancing a simulated clock, dispatching the calls that drive the system into its precondition — and must never absorb the act or the assertions. Hiding any phase makes the test an **Obscure Test** / **Mystery Guest** (Meszaros, *xUnit Test Patterns*): the reader cannot see the cause-and-effect between setup and verification without hunting through fixtures, and defects hide in the parts they cannot see — which is why readability here is a **correctness** concern, not cosmetics. Two concrete tells: (a) a **single-use** setup fixture (consumed by exactly one test) that hides that test's arrange — no reuse benefit, pure indirection; inline its body into the test. (b) **Time control** (`sleep`/a clock advance/an injected start time) buried in a fixture — the advance *is* the scenario and must be a visible line in the body. **A too-large arrange is a design signal, not a licence to hide it.** When setup is so heavy it "needs" a helper to stay readable, the production code — not the test — is at fault: a missing test seam, an un-injected collaborator, or a SUT carrying too many responsibilities (SRP). Fix the code (add the DI seam, split the responsibility, introduce the collaborator) so the arrange shrinks; relocating the complexity into a fixture/helper only moves the smell out of sight and buys the Obscure Test back. A setup fixture earns its place *only* when it is shared by more than one test **and** sets up genuinely *ambient environment* (environment variables, the fake CLIs' config, telemetry, registries) — never the specific arrange/act of one scenario. **Whether a given construction belongs in a fixture, factory, or inline is owned by `pytest-factoryboy`** — load it and apply its patterns.

# Review Scope

When this skill is invoked manually or for a feature branch review, scan ALL new and modified test files in the git working tree — not just the file currently being edited. Use `git status` to identify untracked (`??`) and modified (`M`) test files. Every test file touched by the branch must pass these quality gates.

**Infrastructure reuse check**: During review, read conftest.py and any test utility modules in the same package. Compare local helpers in the branch's test files against what's already shared. Flag any local helper that reimplements shared infrastructure or any inline class that duplicates a shared fake.

**Rule on the pattern once, then apply it uniformly — do not adjudicate each instance.** When the same structural shape recurs across files (e.g. "a 2-field result asserted field-by-field," "a `_section_lines` section assertion," "a one-line `Runtime(...)` wrapper"), decide the verdict for that *shape* a single time and apply it to every instance. Adjudicating case by case is how a review gives **opposite verdicts to identical patterns** — the failure mode that triggered this guidance: a prior pass confirmed one case in a test file as hard and refuted three of the same shape, and split the three identical `_section_lines` cases 2-hard/1-refuted. If you find yourself reaching a different verdict on a shape you have already ruled on, that is a signal your *rule* is underspecified — sharpen the rule (and the skill), don't emit the contradiction. Verifier/sub-agent per-case splits on a recurring shape are unreliable for the same reason; trust the pattern-level rule over a per-instance verdict.

# Per-Method Review Checklist

For each test method in the review scope, mechanically check these — do not skip any step or rely on the test "looking reasonable":

1. **Scan imports and fixtures for `patch`, `MagicMock`, `Mock`**. For each occurrence, verify the target crosses a process boundary (HTTP, cloud SDK, external credential). If it patches an internal function, factory, module-level callable, or collaborating class — flag it. **Also scan for `class X(<SharedFake>)`** (e.g. `class …(RecordingJudge)`, `class …(ScriptedGemini)`): if the overridden method contains an `assert`, a read of another subsystem (the judgement cache, files on disk), or an accumulator that exists only to prove the override ran, flag it (gate 2, cross-layer subclassing) — use the fake directly and assert on its in-layer state in the test body.
2. **Read every `assert` line**. For each one:
   - Does it use `==` against a complete expected value? If it uses `len()`, `in`, `>`, or single-field access (`.body["field"]`, `.name`), flag it — the full value should be asserted unless object equality is impossible (no `__eq__`, generated ids, timestamps). **Also flag a run of separate `==` lines that together cover every field of a result type that has `__eq__`** — "I checked all the fields individually" is still a gate-4 violation; consolidate to one whole-object `==` so fields added later stay guarded. *`in` exception:* don't flag when the asserted fragment is exact and complete and the surrounding value is a larger composite a **different component** owns, so a whole-value `==` would pin that other component's content rather than the SUT's (gate 3 exception) — and remember "different component owns it" turns on who *authors the content* (a loader/formatter), not on the SUT running the `join`. A fragment that is partial, or one carved out of the SUT's *own* return value, is still a flag.
   - If asserting a collection: is the entire collection content asserted, or only count / one element? `assert len(x) == 1` followed by a field check on `x[0]` is incomplete — assert `x[0].body == {...}` or the equivalent full structure.
   - If asserting an object without `__eq__`: are ALL observable fields checked, not just the one the test name mentions?
3. **Scan for result-normalization before the assertion**. Look for `replace(`, `model_copy(update=`, `model_dump(exclude=`, or a list/dict comprehension over the SUT's output that rebuilds it just before `==`. If the test post-processes the *actual* result to make it match the expected object, flag it (gate 12): each stripped field is now unguarded. The fix is to assert the noisy field's meaningful part directly and leave the rest of the object asserted normally — or to drop to a narrower seam that produces no noise.
4. **For eval tests, inspect `Dataset` and `Case` definitions** against the eval guidelines. Flag: expected values in evaluator constructor arguments or metadata; custom evaluators that duplicate a built-in; a case-level evaluator every case shares; one input split across several cases; a shared runner class, `retry_task`, or a second, hand-rolled report assertion (gate 7's scope note: `JudgeEvalRunner` and `codeguard eval` are product features, not covered); and an `EqualsExpected()` case whose expected output is `None`, which the evaluator skips.
5. **Check for duplicate fixtures and conftest imports** — flag a fixture this file redefines when conftest already provides it, and any `from conftest import <Name>` (conftest is fixture-discovery, not a re-export hub — import types from their defining module). Rules in the `pytest-factoryboy` skill.
6. **Check helper scope** (gate 10) — flag a helper that, beyond setting up, *computes* a value production also computes (imports the same builder/allocator, or is named after one scenario/domain), or *ends by calling a method/attribute on the object it built and returning that* (`return x.method(...)` / `return build_x(...).attr` rather than `return x`) — true even when the method isn't the one under test. Tell: the helper's last line reaches past the constructed object to a call/attribute result. **Do not flag the delegated-output exception:** calling a production function in the *expected value* is fine when the value is a deterministic output field the SUT *delegates* to a collaborator, its inputs are asserted in the same expected object, and the collaborator's function is pinned independently by its own test — that's a consistency check, not shadowing (see reference). **Also flag the action-wrapper (species c):** a helper *named for an action* (`rejudge_*`, `advance_*`, `complete_*`) that takes `(sut, ..., result)`, asserts on the handed-in `result`, drives the next step (a second `judge(...)`/`run(...)` call), and returns the new `result` — it hides both the act and spec assertions behind a name; common in multi-step tests where the change-and-rerun dance repeats. Fix: inline the act in the test body; simulate out-of-band actors through the boundary fake (the request the fake CLI or fake model received), not a query of the SUT's internal state; drop assertions a unit test already owns (gate 1) rather than burying them. See [references/helper-and-integration-gates.md](references/helper-and-integration-gates.md).
7. **Check for signal** (gate 1) — flag if the answer to *what change to my code would make this fail?* is (a) tautology (transcribes the SUT's own declarations), (b) framework behavior (a Pydantic/stdlib guarantee, no decision of yours under test), or (c) redundancy (no behavior left unverified). Caution: a rigorous-looking test can still be a tautology (defect is the *expected value's origin*), and a `Field(le=100)` rejection is *your* decision, not a framework echo. See [references/redundant-tests.md](references/redundant-tests.md).
8. **For an integration/e2e test, name the wiring bug it alone catches** — a mismatched key, an unregistered ref, a mis-ordered step that slips past every unit test yet turns this red. Can't name one ⇒ redundant (see "Integration tests must earn their level").
9. **Scan helper/factory signatures** (gate 13) — flag hidden parameters (`.pop(` over a `**kwargs` bag, a hand-rolled `raise TypeError("unexpected"`), test-only `…Resources`/`…Setup` bundles, post-build attribute injection, and alternative-input branching; the rules and fixes are in the `pytest-factoryboy` skill.
10. **Audit each local `_make_*`/`_build_*`** (gates 2 + 5 + 14) — flag reuse failures, single call sites, dead params, thin-wrapper shims, and production-factory/derivation bypass; the rules and fixes are in the `pytest-factoryboy` skill.
11. **Check parent/child setup direction** (gates 5 + 10) — flag child-only helpers/factories used outside child-SUT tests; tests carry the parent creator's result and correlation per the `pytest-factoryboy` skill.
12. **Scan for module-level construction constants** (gate 15) — flag any `SCREAMING_SNAKE` value that constructs domain objects or stands in for an identity a test asserts on; bare opaque-token scalars are exempt. Rules in the `pytest-factoryboy` skill.
13. **Scan for module-level helper functions that construct test data or harness** (gate 16) — any `def _helper(...)` at module scope whose body constructs and returns a test object (a model, binding, request, verdict, or other domain object) OR assembles the test harness (a judge, a repo, an execution context) bypasses the DI graph. Flag it; the correct replacement is governed by the `pytest-factoryboy` skill (a fixture-returning-closure is **not** an accepted fix). **Do not flag** trivial callbacks the SUT or a framework hook takes as an argument (e.g. `def _no_answer(messages, info): raise AssertionError`) — these are callbacks passed to `FunctionModel(...)` or the SUT, not construction helpers.
14. **Check that each phase lives in the test body** (gate 17) — for each test, confirm arrange, act, and assert are all visible in the method. Flag a fixture/helper that performs an *arrange action* (starts a process/job, advances a clock via `sleep`/a clock advance, dispatches the calls that establish the precondition) rather than merely supplying a constructed thing, and flag any fixture that hides the act or an assertion. **SUT tell:** a test parameter that is the object the test acts on ⇒ flag it. **Returning a real object does not exempt it** — the tell is what the fixture *does to build* the value, not what it returns; a fixture that starts a process and sleeps before returning a handle is a hidden arrange. **Single-use tell:** a setup fixture consumed by exactly one test ⇒ inline its body into that test. **Too-large-arrange tell:** if the setup is only tolerable once hidden, treat it as a missing seam/collaborator/SRP violation in the SUT and fix the production code, not the test. A setup fixture is legitimate only when shared across tests *and* setting up ambient environment (environment variables/fake CLI config/telemetry/registries), not one scenario's arrange.

# Integration tests must earn their level

An integration test is justified only when it catches a **wiring** bug that no unit test on either side of the seam can — a mismatch *between* components, not behavior *within* one. Name the specific defect it alone catches (a key two components must agree on, a ref one side must register, a pipeline ordering). If the honest answer is "it re-runs generic behavior with a real type plugged in," it is a **domain-variant replay** and fails the redundancy gate (Defect 3 in [references/redundant-tests.md](references/redundant-tests.md)). To flag in review, trace each step of the chain to the unit test already covering it; if the only new thing is a real type combined with generic plumbing, delete it and (if the seam lacks one) add a synthetic-domain case to the mechanism's suite. See [references/helper-and-integration-gates.md](references/helper-and-integration-gates.md).

# E2E and Integration Test Exceptions

In end-to-end tests that exercise a specific path (routing, orchestration, error flow), agents not under test may use `TestModel()` with no custom output when the test's purpose is path correctness, not extraction quality. This avoids coupling e2e tests to unrelated agent output shapes. The test name or docstring should make the routing focus explicit.

This exception is about *mocking depth* in a justified path test — it does not exempt a test from earning its level. A workflow-path test still must catch a routing/orchestration bug no unit test can; "earn the level" and "mock only at the boundary" are independent requirements.

The exception covers mocking depth **and nothing else**. It does not license burying the act-under-test or its assertions in a helper. Gate 10 still applies in full: a multi-step test may use a setup-only helper that *builds a component* (a judge, a repo, files), but the act that advances or exercises the SUT — the `review(...)` call, the second `judge(...)` call — stays inline in the test body, and every behavioral assertion stays visible at the call site. A helper that takes `(judge, request, result)`, asserts on `result`, then calls `judge.judge(...)` and returns the next `result` is the canonical violation: it hides both the act *and* spec assertions behind a name, so a reader of the test cannot see what is being driven or checked. Out-of-band actors (a judge CLI subprocess, an external callback) are simulated **inline** by reading the boundary fake and running the real component — not wrapped in an action-helper. If the inline act repeats verbatim across many turns and the repeated assertions duplicate what a unit test already owns, drop the redundant assertions (gate 1) rather than hiding them in a helper.
